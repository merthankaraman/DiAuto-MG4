**Severity:** High  
**CVSS v3.1 Base Score:** 7.5 (High)  
**Components:**

**Introduced in:** Commits `19caaec` / `42849a3` (PR #2, v1.9.x series)  
**Affects:** All MG4 / SAIC-based vehicles running DiAuto-MG4 ≥ v1.9.0

---

### Description

`ArpNudger` is designed to work around MG4 head units that have ARP replies disabled. It sends UDP packets to multiple IP addresses in the vehicle's subnet to trigger ARP broadcasts, thereby revealing the head unit's MAC address.

Three compounding issues make this component hazardous:

#### 1. Missing `stop()` on Error Paths

`ArpNudger.stop()` is called **in exactly one location**: when `serverSocket?.accept()` successfully accepts a TCP connection. If the connection attempt fails for any reason (Bluetooth handshake error, Wi-Fi disconnection, credential timeout, user cancellation), `stop()` is **never invoked**. The coroutine continues sending UDP packets for the full 60-second duration (`MAX_NUDGE_DURATION_MS`).

#### 2. Uncontrolled Broadcast Storm

The nudger sends one UDP datagram per 150ms to up to 50 IP addresses per cycle:
- 50 hosts × (60,000ms / 150ms) = **~20,000 UDP packets** per failed connection attempt
- Each packet triggers an ARP request broadcast on the vehicle's Ethernet segment

#### 3. Hardcoded /24 Subnet Assumption

Target addresses are generated by replacing the last octet of the host IP:

```kotlin
val target = byteArrayOf(raw[0], raw[1], raw[2], lastOctet.toByte())
```

If the vehicle's hotspot or a static network configuration uses a different subnet mask (e.g., `/20` or `/28`), the nudger will:
- Target addresses outside the actual network segment
- Hit broadcast addresses of adjacent subnets
- Send packets to potentially active devices on neighboring networks

### Impact on Vehicle IVI System

| Impact Area | Description |
| :--- | :--- |
| **ARP table saturation** | Up to 50 `INCOMPLETE`/`FAILED` entries are created in the Linux kernel neighbor table. On embedded automotive systems with limited ARP cache, this can evict entries for critical appliances (T-Box ECU, Ethernet gateway) |
| **Network congestion** | Sustained ARP broadcast storms degrade real-time CAN-over-Ethernet or diagnostic traffic on the vehicle bus |
| **Resource leak** | The `DatagramSocket` and coroutine job remain allocated even after the parent connection flow has abandoned the attempt |
| **Repeated triggering** | Combined with the reconnection loop (CVE-DIAUTO-2026-002), each failed reconnection cycle spawns a new ArpNudger instance |

### Recommended Fix

1. **Call `stop()` in a `finally` block** around the connection attempt, not only on success.
2. **Use structured concurrency**: Tie the nudger's coroutine scope to the parent connection job so cancellation propagates automatically.
3. **Respect the actual subnet mask**: Use `NetworkInterface.getInterfaceAddresses()` to retrieve the prefix length instead of assuming `/24`.
4. **Rate-limit and cap total packets**: Introduce an exponential backoff rather than a fixed 150ms interval.

```kotlin
// BEFORE (vulnerable)
fun start(scope: CoroutineScope, hostAddress: InetAddress) {
    job = scope.launch {
        // sends UDP packets for 60 seconds, never stopped on error
    }
}

// AFTER (fixed)
fun start(scope: CoroutineScope, hostAddress: InetAddress): Job {
    return scope.launch {
        try {
            // send UDP packets with backoff
        } finally {
            stop()  // always cleanup
        }
    }
}
```
